Agility CMS had grown the way most successful products do. Features shipped fast, teams worked in parallel, and over a few years the interface drifted. Buttons came in a dozen subtly different shapes. The same action looked different on every screen. Engineers rebuilt the same patterns over and over because there was nowhere to find the canonical version.

I joined to fix the root cause, not the symptoms. That meant a single design system, built from zero, that the whole product could stand on.

## The problem underneath the problem

The visible issue was inconsistency. The real issue was that design and engineering had no shared language. A handoff meant redlines, screenshots, and a long thread of clarifying questions. By the time a feature shipped, it had drifted again.

So I scoped the work around one outcome that mattered to everyone: shorten the distance between a design decision and working code.

## A system, not a sticker sheet

A design system is only as good as the decisions baked into it. I started with tokens, because tokens are the contract. Color, type, spacing, radius, and motion all resolved to named values that design and code referenced identically.

<TwoColumn>
  <Fragment slot="left">
    **Design side.** Tokens lived in the Figma library as variables. A designer never picked a raw hex value again. They chose a semantic token, and the system kept everything coherent.
  </Fragment>
  <Fragment slot="right">
    **Engineering side.** The same tokens compiled to CSS custom properties. When a value changed, it changed in one place and propagated everywhere, with no hunting through stylesheets.
  </Fragment>
</TwoColumn>

On top of the tokens sat the components. Each one shipped with its anatomy, its states, its accessibility behavior, and a usage note explaining when not to use it. The last part matters more than people expect. A system that only says yes grows into the same mess it replaced.

## Redrawing the product on top of it

With the foundation in place, I rebuilt the core product surfaces. The content editor was the highest-traffic screen, so it went first. The brief was simple to say and hard to do: make a deeply flexible tool feel calm.

### What changed in practice

- One button, one input, one table. Defined once, used everywhere.
- Documentation that lived next to the code, so it stayed true.
- A review process where design and engineering spoke the same vocabulary.

The result was less back and forth. Handoff stopped being a translation step and started being a reference. Design-to-dev friction dropped by roughly half, and the brand finally read as one product instead of ten.

## What I would carry forward

The system worked because it was opinionated and documented, not because it was large. The smallest, most boring decisions, naming a token well, writing one clear usage note, are the ones that compounded. That is the part I take into every project since.
